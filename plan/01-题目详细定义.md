## 一、项目介绍

《个人信息保护合规审计管理办法》（国家互联网信息办公室令 **第 18 号**）自 **2025-05-01 施行**，确立了个人信息处理者的**定期合规审计义务**：处理超过 **100 万人**个人信息的处理者应**每两年至少开展一次**合规审计，处理超过 **1000 万人**的应履行更严格义务（含专业机构审计要求）。配套标准 GB/T 35273-2020《个人信息安全规范》与 GB/T 42574-2023《个人信息处理中告知同意的实现指南》构成审计的规范依据。企业侧的真实痛点是：**我是否触发审计义务、多久做一次、审计要查哪些项、查出问题怎么留证据、怎么出报告**——目前开源工具集中在"App 隐私 API 调用技术检测"（如 PrivacySentry/Python 静态扫描类），**审计办法口径的"合规审计工作台"开源近乎空白**。

本项目要求开发一款**个人信息保护合规审计工作台**：把"审计触发判定 → 检查单逐项核查 → 证据链留痕 → 问题分级 → 审计报告导出"整条链做成**本地化、可复现、可留痕**的工具，核心特色是**版本化审计规则集**（沿用系列 versioned ruleset 模式，把办法/标准条款编码为可执行的审计检查项规则包）+ **确定性门槛引擎**（处理规模与频次判定不留模糊）+ **证据链**（每个核查结论挂条款依据与证据附件）。

## 二、任务要求

> 首期范围限定为 **《审计办法》（网信办令第 18 号）+ GB/T 35273-2020 核心章节 + GB/T 42574-2023 告知同意**三份依据；其余配套标准留扩展。全部模块遵循"**未挂原文核对不得落库/生效/进入判定路径**"的确定性纪律。

### 1）审计触发与频次判定引擎（确定性内核，亮点）

- 输入：处理个人信息的人数规模、是否处理敏感个人信息、处理者类型等参数；
- 按办法门槛**确定性判定**：是否触发审计义务、应适用的审计频次（如超 100 万人每两年一次）、是否需专业机构审计；
- 输出**判定结论 + 条款依据**（结论旁挂条号），边界值（等于 100 万/1000 万）显式处理并在基准中枚举验证；
- 判定参数与门槛值一律从规则包读取，禁止硬编码。

### 2）审计检查单引擎（53 项级规则化检查）

- 把办法与标准的审计要点编码为**结构化检查项**（编号、类别、条款依据、核查方式、判定标准、证据要求）；
- **检查单分层**：制度层（政策/组织/培训）、流程层（告知同意/最小必要/委托处理/共享转让）、技术层（访问控制/加密/去标识化/日志）、响应层（个人权利响应/安全事件/投诉处理）；
- 支持**自动核查项**（可从结构化输入判定的，如"是否提供撤回同意入口"由表单字段判定）+ **人工核查项**（需审计员录入结论与证据）；每项输出 符合/部分符合/不符合/不适用 四态 + 说明；
- 检查项库 JSON 化，每条挂条款依据与 status，未核对不得生效。

### 3）证据链留痕（交付物进入工作流，亮点）

- 每个检查结论可**挂载证据**（本地文件引用：截图/文档/日志片段），记录证据来源、采集时间、责任人；
- **不可篡改**：证据条目计算 sha256 指纹随审计底稿固化，报告导出时附证据清单与指纹，供复查对照（沿用系列"指纹防篡改"招牌模式）；
- **审计底稿**可整体导出/导入，支持跨会话续做与复核。

### 4）问题分级与整改跟踪

- 按严重程度分级（高风险/中风险/低风险/建议），分级标准挂条款依据；
- 生成**整改台账**（问题 → 依据条款 → 整改建议 → 责任人 → 期限 → 状态），支持导出；
- **风险提示 ≠ 法律判定**的伦理框架：工具输出为"合规检查发现"，明确声明不构成法律意见。

### 5）审计报告导出（可核证交付物）

- 一键导出**合规审计报告**（Markdown + DOCX/XLSX）：含审计范围、依据清单、触发判定结论、检查单全项结果、问题清单与整改台账、证据清单与指纹；
- 报告头固定输出**规则包坐标**（依据版本 + 版本号 + 生成时间），保证可复现与可比对；
- 报告模板可配置（企业自审版 / 第三方机构版）。

### 6）版本化审计规则集（工程亮点）

- 规则包按 **`依据文件 × 版本`** 组织（审计办法令第 18 号、GB/T 35273-2020、GB/T 42574-2023…），条款变更即升版本；
- 规则包 JSON 化，每条挂文号/标准号与 status（`verified`/`pending`）；切换规则版本即切换检查单与门槛值；
- **依据联动**：每项检查结论可回溯到具体条款。

### 7）内置评测基准（零 API 依赖）

- **门槛边界基准**：100 万/1000 万等门槛的边界值（恰好等于、上下 1 人）枚举验证判定正确性；
- **检查项自洽基准**：规则包条款引用完整性、四态判定逻辑覆盖、证据要求非空；
- **合成审计场景基准**：程序化构造带真值的合成审计场景（如"某企业处理 120 万人信息但未做审计"应判触发 + 未达标），零 API 依赖可重复，指标写进 README。

## 六、边界与非目标

- **不做**：不做 App/小程序 API 调用的动态/静态技术检测（属另一细分，PrivacySentry 等已占）；不做法律意见出具；不做自动化数据爬取核查；不对接监管申报接口。
- **首期范围**：办法令第 18 号 + GB/T 35273-2020 + GB/T 42574-2023 三份依据；其余标准留扩展。
- **合规红线**：**全本地处理存储、零上传**；审计证据可含敏感信息，工具须支持**脱敏/本地留存**，默认不联网；**免责声明强制**：输出为合规检查发现，不构成法律意见，正式合规结论以监管口径/执业机构意见为准；规则包未挂原文核对（status=pending）不得进入判定路径。
- **数据纪律**：审计场景一律使用**合成/脱敏数据**，禁止真实个人信息样本入库；假号段（如 19900000000 类）、合成身份信息按白名单登记；证据样本仅留结构说明。 <!-- audit-allow: 合成测试号段白名单，非真实号码 -->
- **品牌隔离**：不复制姊妹项目代码；文档不提其余项目业务领域。
