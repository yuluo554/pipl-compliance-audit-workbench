# 04 模块详设

> 上游：[03-架构与技术选型.md](03-架构与技术选型.md)。本文定规则包 schema、检查项模型、门槛判定语义、证据与报告模板。
> 版本：v1（M0 定稿，2026-10-13）

## 一、规则包 schema（`data/rules/ruleset-*.json`）

```jsonc
{
  "schema_version": "1.0",
  "ruleset_id": "pipl-audit-2025",          // 规则集稳定身份键（跨版本不变）
  "version": "2025.1",                      // 规则包版本（条款变更即升）
  "generated_at": "2026-10-13T00:00:00Z",   // 生成器固定值（非系统时钟）
  "basis": [                                // 依据清单（报告头坐标）
    {"code": "网信办令第18号", "title": "个人信息保护合规审计管理办法",
     "effective_date": "2025-05-01", "status": "verified", "source": {...}},
    {"code": "GB/T 35273-2020", "title": "信息安全技术 个人信息安全规范",
     "effective_date": "2020-10-01", "status": "verified", "source": {...}},
    {"code": "GB/T 42574-2023", "title": "信息安全技术 个人信息处理中告知和同意的实施指南",
     "effective_date": "2023-12-01", "status": "verified", "source": {...}},
  ],
  "thresholds": [ /* 门槛规则数组，见 §二 */ ],
  "checklist":  [ /* 检查项数组，见 §三 */ ]
}
```

**status 语义**（全库统一）：
- `verified`：已挂官方原文核对，必须带 `source`{`channel`, `url`, `checked_at`}；
- `pending`：待核对，**不得进入判定路径**（`effective_ruleset()` 门控拒绝）。
- `source.url` 可空（如标准全文公开页需登录），但 `channel` 与 `checked_at` 必填。

## 二、门槛规则模型（`thresholds[]`）

门槛用**声明式规则**表达，而非代码分支（防硬编码，满足 NFR-5）：

```jsonc
{
  "id": "TH-SCALE-PERIODIC",
  "param": "scale",              // 输入参数名
  "op": ">",                     // 比较算子: > >= < <= == !=
  "value": 10000000,             // 门槛值（数值只能在此出现）
  "conclusion": "trigger_periodic_audit",   // 结论码
  "frequency": "每两年至少开展一次合规审计",   // 适用频次（来自条款要点）
  "clause": {"basis": "网信办令第18号", "article": "第四条", "point": "<条款要点>"},
  "status": "verified",
  "source": {"channel": "cac.gov.cn", "url": "...", "checked_at": "2026-10-13"}
}
```

> 已核对的条款（data/README §二·1）：**第四条** 超过 **1000 万人**每两年一次（`op=">"`）；**第十二条** **100 万人以上**须指定负责人（`op=">="`）；**第五条** 保护部门可要求委托专业机构审计（多条件情形，非纯规模门槛，M2 建模）。

**判定算法**：门槛引擎按 `param` 取输入值，按 `op`/`value` 求值；命中多个门槛时按**最严格者**（结论严重度序）归并。所有比较都在 `Decimal`/整数域（规模为人数，整数比较，无浮点尾差）。

**边界处理**：`op` 决定边界归属（`>` 不含等于，`>=` 含等于）；"恰好等于门槛""上/下 1 人"由基准枚举验证（FR-7.1）。

## 三、检查项模型（`checklist[]`）

```jsonc
{
  "id": "CHK-DOC-001",
  "category": "制度层",            // 制度层/流程层/技术层/响应层
  "title": "是否制定个人信息保护政策",
  "clause": {"basis": "GB/T 35273-2020", "article": "5.x", "point": "<要点>"},
  "method": "manual",             // auto=可结构化判定 / manual=审计员录入
  "auto_field": null,             // method=auto 时：绑定的输入字段名
  "criteria": "政策文本已制定并公开发布 = 符合；已制定未公开 = 部分符合；未制定 = 不符合",
  "evidence_required": true,      // 证据要求（自洽基准断言非空）
  "status": "verified"
}
```

**判定流程**：
1. `effective_ruleset()` 过滤掉 `status=pending` 的检查项（NFR-6）；
2. 对 `method=auto` 项：读参数卡 `auto_field` 值 → 按 `criteria` 映射为四态；
3. 对 `method=manual` 项：读底稿中审计员录入结论；未录入 = `unknown`（未观测）；
4. `only_if` 门控（可选）：门控值不满足 → `not_applicable`（skipped），不计违规、不计分母；
5. 汇总：见 §四。

## 四、汇总判定语义

```
applicable = 检查项中状态 ∈ {compliant, partial, noncompliant} 的项
if applicable 为空:                      summary = not_assessed   # 绝不输出 compliant
elif 存在 noncompliant:                  summary = noncompliant
elif 存在 partial:                       summary = partial
else:                                    summary = compliant
```

**"没查出问题"与"没检查过"必须可区分**：`unknown`（未观测）计入"待人工确认"计数，不进 `applicable` 分母；`not_applicable` 不计入分母。

## 五、证据链模型

```jsonc
// 底稿 draft.json
{
  "schema_version": "1.0",
  "ruleset_id": "pipl-audit-2025",
  "ruleset_version": "2025.1",
  "audit_scope": {"subject": "示例企业（虚构）", "period": "2026"},
  "input_card": { "scale": 1200000, "sensitive": true, "subject_type": "processor" },
  "threshold_result": { /* 门槛判定结论 + 依据 */ },
  "item_results": [
    {"item_id": "CHK-DOC-001", "state": "noncompliant", "note": "...",
     "evidence": [
       {"evidence_id": "EV-0001", "source": "制度文件截图（结构说明）",
        "collected_at": "2026-10-01", "owner": "审计员A",
        "file_ref": "<本地文件引用，不入报告正文>", "size": 12345,
        "sha256": "<64hex>"}
     ]}
  ],
  "findings": [ {"finding_id": "F-001", "item_id": "...", "risk": "high",
                 "clause": {...}, "recommendation": "...", "owner": "...",
                 "due": "2026-12-31", "status": "open"} ],
  "disclaimer": "本工具输出为合规检查发现，不构成法律意见……"
}
```

**指纹固化**：每条证据的 `sha256` 随底稿固化；底稿导出产物自身 sha256 写进随附 `evidence.json`。

## 六、报告模板（两种）

| 节 | 企业自审版 | 第三方机构版 |
|---|---|---|
| 报告头 | 规则包坐标（依据版本+版本号+生成时间） | 同左 + 审计机构/受托信息占位 |
| 审计范围 | 主体/期间/依据清单 | 同左 + 委托事项 |
| 触发判定 | 结论 + 条号 | 同左 |
| 检查单全项 | 全项四态 + 说明 | 同左 + 核查方式标注 |
| 问题清单 | 分级 + 依据条款 | 同左 + 复核人栏 |
| 整改台账 | 问题→建议→责任人→期限→状态 | 同左 |
| 证据清单 | 来源/时间/责任人/指纹 | 同左 |
| 声明 | 免责声明 | 同左 + 签署栏 |

**报告产物确定性**：Markdown 无时间戳（时间取底稿显式字段）；DOCX/XLSX 落盘后统一"固定时间戳 + `create_system=0`"重写 zip 收口（`report/docxutil.py` 供全通路复用）。

## 七、基准设计（`benchmark/`）

| 基准 | 内容 | 真值来源 | 指标 |
|---|---|---|---|
| B1 门槛边界 | 办法门槛（1000 万/100 万）的"恰好等于/±1 人"枚举 | 规则包门槛值 ± 邻域 | 判定正确率 |
| B2 检查项自洽 | 条款引用完整性、四态逻辑覆盖、证据要求非空 | 规则包自身 | 断言通过率 |
| B3 合成场景 | 程序化构造带真值的审计场景 | `data/truth/`（生成器产出） | 触发判定准确率 / 四态判定准确率 / 误报率 |

**真值语义单一实现源**：`benchmark/cases.py` 的 `expected_summary()` / `observed_nonpass()` 供测试与基准共用（防"基准说达标、测试说不过"的双口径漂移）。
**不许改真值凑引擎**：发现引擎与真值冲突 → 先判定谁对（回查条款/门槛语义）→ 修代码而非改真值；确认真值错则记录理由后改真值。
